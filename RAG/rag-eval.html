01 — 核心心法

拆兩段量

這是整份文件最重要的一句話，也是面試最容易分出高下的地方。只講「我用 RAGAS 跑分」的人在這裡就停了。

檢索端 Retrieval 生成端 Generation

兩個探針分別掛在管線的兩個位置。只看端到端分數，等於把探針拆掉只留一顆總電表。

拆開之後，除錯就變成可決策的：Recall 高但 Faithfulness 低，代表資料撈對了，問題在 prompt 或模型；Recall 低，那不管生成端多強都救不回來，先回去修 chunking、embedding 或 hybrid search。這個因果順序本身就是一個完整的面試答案。

02 — 檢索端

檢索端指標

不需要 LLM，純數學。便宜、穩定、可以每次 commit 都跑。先把這一端量準，再花錢量生成端。

指標在測什麼什麼時候該看它
Recall@k正確文件有沒有出現在前 k 筆裡最重要。這裡漏了，後面再強都救不回來
Precision@k前 k 筆裡有幾筆是真的相關context window 有限、雜訊會干擾 LLM 時
MRR第一個正確答案排名的倒數平均只需要一筆正確文件的場景，例如 FAQ
NDCG@k同時考慮排序位置與分級相關性評估 rerank 效果一定看這個
Hit RateRecall@k 的二元版，有或沒有快速看板、CI 門檻

NDCG 與端到端品質的相關性比二元的 precision／recall 更強，因為 LLM 確實會受 context 順序影響。

面試陷阱題

「Recall@k 的 k 為什麼不能無限調大？」

k 越大 Recall 一定漲，但 Precision 掉、context 變長、成本變高，而且 LLM 會被雜訊干擾（lost-in-the-middle：長 context 中段的資訊最容易被忽略）。所以實務做法是 retrieve k=50 → rerank → 取 top 5。答得出後半句才算過關。

03 — 生成端

生成端指標

這一端要用 LLM 當評審，所以貴、慢、而且會有偏誤。不要每次 commit 都跑全量。

指標在測什麼生產門檻
Faithfulness答案的每個 claim 都能從 context 找到支持嗎 —— 直接測幻覺> 0.80
高風險 > 0.90

Context Precision撈回來的 context 有多少比例真的被用上視場景

RAG Triad

TruLens 把前三個包成一個好記的三角形。面試時用這張圖開場很有效 —— 一句話交代完整個評估架構，而且對方立刻知道你不是只會跑 library。

04 — 評審的評審

LLM-as-Judge 的坑

大部分人只知道「用 GPT-4o 當評審」，不知道評審本身要先被評審。這題答得出來就是資深。

評審沒校準過，後面所有數字都是假的。

先驗證 judge

抽 100 題人工標註，跟 judge 的判斷算一致性（Cohen's kappa）。kappa 太低，代表你的整個 eval 建立在流沙上 —— 你會根據錯誤的訊號去調 chunk size，然後以為自己在進步。

參考值：GPT-4o 等級的評審在區分「真相關」與 hard negative 上大約有 80% 以上的準確率。夠用，但不是真理。

三個已知偏誤

偏誤症狀
Verbosity bias答案越長分數越高，即使冗詞贅字並沒有增加資訊
Position bias成對比較時，排在前面的選項系統性佔優
Self-preference模型偏好自己家族生成的文字風格

對策

用結構化 rubric（明確寫出每一分的判準）加上強制 JSON 輸出，而不是丟一句「請給 1 到 5 分」。分數會穩定得多，而且每一筆判斷都可稽核 —— 企業場景裡這點比分數本身更重要，因為你得跟法遵解釋為什麼系統說了那句話。

05 — 實務

大廠實際怎麼做

一般人講到 RAGAS 就停了。這一段是真正的分水嶺 —— 差別在於你有沒有把評估當成一套工程系統，而不是一次性的跑分。

分層評估

Unit單一 chunk 能不能被它自己的問題檢索到
Component整條 retrieval pipeline 的 Recall 與 NDCG
End-to-end完整答案的 Faithfulness 與 Correctness
Online真實使用者訊號 —— 這一層才是真相

Golden set 是人工標的

合成資料是起點，不是終點。正式的 eval set 是幾百到幾千題、人工逐題審過的。這件事看起來像雜務，實際上是護城河 —— 模型會換、框架會換，標註過的 golden set 會一直留著。

Regression suite 進 CI

每次改 chunk size、換 embedding、動 prompt，全部自動跑。設門檻：任一指標掉超過 3% 就擋 PR。DeepEval 直接接 pytest 就是為了這件事。

線上訊號才是真相

訊號代表什麼
Thumbs up / down最直接，但回報率低且有自我選擇偏誤
Escalation rate轉真人客服的比例 —— 系統失敗的硬指標
Rephrase rate使用者換句話再問一次，等於上一輪失敗了
Session 長度要看方向：查詢型變長是壞事，探索型不一定

離線分數漂亮、線上爛透，是常態而不是意外。

06 — 除錯

失敗類型分類

不要只看總分，要看錯在哪。把失敗歸類之後優化才有方向，否則你只是在亂調參數然後祈禱分數上升。

失敗類型該修哪裡
檢索沒撈到chunking 策略、embedding 選型、加 hybrid search（BM25 + vector）
撈到了但排很後面加 reranker（cross-encoder）
撈到了但 LLM 沒用prompt 設計、context 排列順序
用了但講錯模型能力、加強 faithfulness 約束與引用要求
語料裡根本沒有要能誠實說「我不知道」
大多數人漏掉這一類

你的 eval set 一定要包含答案不在語料裡的問題，測系統會不會硬掰。這叫 negative testing，是大廠一定做、但教學文章幾乎不提的東西。

沒有這類題目，你的 Faithfulness 分數會虛高 —— 因為你從來沒給過系統說謊的機會。

08 — 語料決定

經典調酒配方

語料的第一要求不是有趣，是你看得懂答案對不對。不懂的領域標不出 golden set，標不出 golden set 就沒有評估，沒有評估就只是做 demo。調酒同時滿足「有趣」和「可驗證」—— 配方對不對，查一下就知道，不需要領域專家。

它剛好是 hard negative 的教科書

下面三杯是同一個 Sour 骨架（基酒＋柑橘＋甜味），只換基酒。文字描述近乎一模一樣，embedding 距離幾乎為零：

Daiquiri 白蘭姆酒 45ml · 萊姆汁 25ml · 糖漿 15ml　shake
Margarita 龍舌蘭 35ml · 萊姆汁 20ml · 橙酒 20ml　shake
Sidecar 干邑白蘭地 40ml · 檸檬汁 20ml · 橙酒 20ml　shake
Q：「有沒有酸酸甜甜、帶柑橘的短飲？」
→ 三杯的向量分數幾乎相同，排序等於擲骰子
→ 想穩定命中，必須靠 metadata filter（基酒）或 rerank
→ 這就是你示範 hybrid search 價值的最佳舞台

四種題型天然齊備

題型範例
單跳事實「Negroni 的三種材料比例是多少？」
Multi-hop「我家只有琴酒和甜苦艾酒，能調什麼？」需要跨多筆配方彙整
口語化改寫「有沒有不苦、女生會喜歡的？」術語與白話的語意落差
Negative「Negroni 的抹茶版本比例？」語料裡沒有 —— 測會不會硬掰

還有三個工程上的好處

結構化 metadata 現成。每筆配方天然帶有基酒、手法（shake／stir／build）、杯型、IBA 分類、酒精強度 —— 直接拿來練 metadata filtering 與 hybrid search，不用自己造。

量剛好。IBA 官方 77 款加上經典擴充約數百筆，筆電跑得動，一次實驗幾分鐘跑完，你能快速迭代而不是等一整晚。

Demo 有記憶點。面試時你打開一個會推薦調酒的系統，對方一定會多問兩句 —— 那正是你把 Recall、rerank、negative testing 講出來的機會。

09 — 合成資料

合成 Eval Set 的正確做法

合成解決的是「標註成本」，不是「你看不懂答案」。第 4 步不能省 —— 那一步就是你的判斷力派上用場的地方。

  1. 取一個 chunk 從切好的語料隨機抽樣，注意涵蓋不同基酒與長度分布，不要全部擠在琴酒那一區。
  2. 叫 LLM 出題 提示詞的關鍵是「出一個客人真的會在吧台問的問題」。不加這個限定，你會得到一堆「本文提到的三種材料是什麼」這種考卷式問題。
  3. 那個 chunk 自動就是 ground truth 這是整個手法的精髓 —— Recall@k 與 NDCG@k 完全免費拿到，不需要任何人工標註。
  4. 人工抽審 10 到 20 個百分比 砍掉爛題：答案直接抄在問題裡的、模糊到無法判斷的、根本不是人會問的。這一步不能省。
  5. 補上三種進階題型 只做前四步的 eval set 太簡單，分數會虛高。必須補：multi-hop、negative、口語化改寫。上一節的四種題型就是照這個清單設計的。

RAGAS 的 TestsetGenerator 做的是第 1 到 3 步。第 4、5 步要你自己補 —— 而這兩步正好是面試時能講出差異化的地方。

10 — 執行

四個階段

刻意不從自己的資料開始。Stage 0 的目的是確認你的指標算得對 —— 公開 benchmark 有 leaderboard，你算出 NDCG@10 = 0.42 可以立刻知道這是好是壞；自己的語料永遠沒有這個參照點。

STAGE 0 拿公開 benchmark 校準程式碼 BEIR 的一個小 dataset，確認手刻的 Recall@k、NDCG 算得對
STAGE 1 調酒語料加手寫 30 題 含那三杯 Sour 的 hard negative。這 30 題是後面所有比較的基準線
STAGE 2 RAGAS 合成擴到 300 題 抽審過濾，補上 negative 與 multi-hop
STAGE 3 接進 CI，每次改動都跑 履歷上最有說服力的一句話來自這裡

「我的 RAG 有一個 300 題的 eval set，換 embedding 讓 NDCG@10 從 0.61 到 0.74，加 rerank 再到 0.82，全部跑在 CI 裡。」

這句話能講出來，你就贏過絕大多數只會 demo 的候選人 —— 因為它同時證明了三件事：你有 ground truth、你做過受控比較、你把它工程化了。

# 第 1 章：從 0 到百萬使用者（加強版）

## 1. 章節核心

本章展示典型網路服務如何從單機逐步演進到可承載大流量的分層架構，重點不是一次到位，而是「按瓶頸漸進升級」。

## 2. 演進階段

### 階段 A：單機

- Web、資料庫、快取都在同一台機器。
- 優點：實作快、成本低。
- 風險：單點故障、資源爭用嚴重。

### 階段 B：Web 與 DB 分層

- 應用層與資料層分離，開始可獨立擴容。
- 這是最關鍵的第一個架構分水嶺。

### 階段 C：負載平衡

- 前置 LB 將流量分散到多台 Web。
- 能處理單節點故障，提升可用性與吞吐。

### 階段 D：資料庫主從複製

- 主庫負責寫，從庫負責讀。
- 好處：讀寫分離、提升讀取吞吐、具備容災基礎。

### 階段 E：快取層

- 熱資料先查快取，未命中再回源 DB。
- 核心目標：降低延遲、保護資料庫。

### 階段 F：CDN

- 靜態資源（JS/CSS/圖片/影片）就近分發。
- 降低源站流量，改善跨區使用者體感。

### 階段 G：無狀態 Web

- Session 外移到共享儲存（DB/Redis）。
- 任一 Web 節點都可服務任一請求，便於水平擴展。

## 3. 關鍵工程要點

- 快取要設計 TTL、淘汰策略（LRU/LFU）、失效機制。
- 主從架構要預想故障切換與資料延遲問題。
- CDN 要有回源與失效（invalidate/versioning）策略。
- 每次擴容前都要先做容量估算，避免盲目加機器。

## 4. 面試講法（可直接套用）

- 先講目前瓶頸（CPU、DB QPS、延遲）。
- 再講對應改造（LB、快取、讀寫分離）。
- 補上故障場景（節點掛掉、快取雪崩、主庫故障）。
- 最後講取捨（成本、複雜度、一致性）。

## 5. 常見追問

- 為何不只做垂直擴容？
- 快取與資料庫不一致怎麼處理？
- 主從延遲影響讀一致性怎麼辦？
- 跨區部署後流量如何導流？

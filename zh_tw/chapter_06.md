# 第 6 章：設計鍵值儲存系統（Key-Value Store）

鍵值儲存系統（Key-Value Store），又稱鍵值資料庫（Key-Value Database），是一種非關聯式資料庫。每個唯一識別碼（Key）與其對應的值（Value）組成一組資料對，這種配對稱為「鍵值對（Key-Value Pair）」。

在鍵值對中，鍵必須是唯一的，對應的值可以透過鍵來存取。鍵可以是純文字或雜湊值（Hashed Value）。基於效能考量，較短的鍵通常較佳。以下是幾個鍵的範例：

- 純文字鍵：`"last_logged_in_at"`
- 雜湊鍵：`253DDEC4`

鍵值對中的值可以是字串、串列（List）、物件等。在 Amazon DynamoDB [1]、Memcached [2]、Redis [3] 等鍵值儲存系統中，值通常被視為不透明物件（Opaque Object）。

本章中，你被要求設計一個支援以下操作的鍵值儲存系統：

- `put(key, value)` // 插入與 key 對應的 value
- `get(key)` // 取得與 key 對應的 value

---

## 理解問題並確立設計範疇

設計上沒有完美的解法。每種設計都在讀取、寫入和記憶體使用之間取得特定的平衡。另一個需要取捨的面向是一致性（Consistency）與可用性（Availability）之間的權衡。本章設計的鍵值儲存系統具備以下特性：

- 鍵值對的大小較小：小於 10 KB
- 能夠儲存大量資料
- **高可用性**：系統反應迅速，即使發生故障也不受影響
- **高擴展性**：系統可以擴展以支援大型資料集
- **自動擴展**：新增或刪除伺服器應根據流量自動進行
- **可調式一致性**（Tunable Consistency）
- **低延遲**

---

## 單機鍵值儲存

設計一個在單台伺服器上運作的鍵值儲存系統相對簡單。直觀的做法是使用雜湊表（Hash Table）將鍵值對儲存在記憶體中。雖然記憶體存取速度很快，但受限於空間，將所有資料都放進記憶體並不可行。針對單台伺服器可以做兩項優化：

- 資料壓縮（Data Compression）
- 僅將常用資料存在記憶體中，其餘存放於磁碟

即使如此，單台伺服器也很快會達到容量上限。若要支援大量資料，就需要**分散式鍵值儲存系統（Distributed Key-Value Store）**。

---

## 分散式鍵值儲存系統

分散式鍵值儲存系統又稱為分散式雜湊表（Distributed Hash Table），它將鍵值對分佈於多台伺服器上。在設計分散式系統時，理解 **CAP 定理（CAP Theorem）** 至關重要。

### CAP 定理

CAP 定理指出，一個分散式系統無法同時滿足以下三種保證超過兩項：

- **一致性（Consistency）**：無論連接到哪個節點，所有客戶端在同一時間看到的資料都相同。
- **可用性（Availability）**：任何發出資料請求的客戶端都能得到回應，即使部分節點離線。
- **分區容錯性（Partition Tolerance）**：分區（Partition）指兩個節點之間的通訊中斷。分區容錯性意味著即使發生網路分區，系統仍能繼續運作。

CAP 定理指出，必須犧牲其中一個特性才能同時支援另外兩個，如圖 6-1 所示。

現今鍵值儲存系統依據其支援的兩種 CAP 特性分類：

- **CP 系統（一致性 + 分區容錯性）**：支援一致性與分區容錯性，犧牲可用性。
- **AP 系統（可用性 + 分區容錯性）**：支援可用性與分區容錯性，犧牲一致性。
- **CA 系統（一致性 + 可用性）**：支援一致性與可用性，犧牲分區容錯性。由於網路故障無法避免，分散式系統必須容忍網路分區，因此 CA 系統在現實應用中並不存在。

### 現實環境中的分散式系統

在分散式系統中，分區是無法避免的。當分區發生時，我們必須在一致性與可用性之間做出選擇。

假設資料複製於三個副本節點 n1、n2、n3（如圖 6-3），n3 發生故障，無法與 n1、n2 通訊：

**選擇 CP（一致性優先）**：必須封鎖對 n1 和 n2 的所有寫入操作，以避免三台伺服器之間的資料不一致，這使系統進入不可用狀態。銀行系統通常有極高的一致性要求，例如銀行系統必須顯示最新的餘額資訊；若因網路分區而發生不一致，銀行系統會在問題解決前回傳錯誤。

**選擇 AP（可用性優先）**：系統繼續接受讀取請求，即使可能回傳舊資料。對於寫入，n1 和 n2 持續接受，當網路分區問題解決後，資料再同步至 n3。

選擇符合使用場景的 CAP 保證，是建立分散式鍵值儲存系統的重要步驟。

## 資料分區

對於大型應用程式，將完整資料集放入單一伺服器是不可行的。最簡單的做法是將資料拆分成較小的分區，儲存於多台伺服器。資料分區時有兩個挑戰：

- 將資料平均分佈於多台伺服器
- 新增或移除節點時，將資料移動量降至最低

第 5 章討論的**一致性雜湊（Consistent Hashing）**是解決這些問題的絕佳技術：

- 首先，將伺服器放置於雜湊環上。在圖 6-4 中，八台伺服器 s0, s1, ..., s7 被放置於雜湊環上。
- 接著，將鍵雜湊到同一個環上，並沿順時針方向找到第一台伺服器進行儲存。

使用一致性雜湊進行資料分區的優點：

- **自動擴展**：伺服器可依據流量自動新增或移除。
- **異質性（Heterogeneity）**：虛擬節點數量與伺服器容量成正比，容量較大的伺服器可分配更多虛擬節點。

## 資料複製

為實現高可用性與可靠性，資料必須非同步複製至 N 台伺服器（N 為可調整的參數）。選取 N 台伺服器的邏輯如下：將鍵映射到雜湊環上的某個位置後，沿順時針方向選取前 N 台伺服器來儲存資料副本。在圖 6-5 中（N = 3），key0 被複製至 s1、s2 和 s3。

由於使用虛擬節點，前 N 個節點可能屬於少於 N 台實體伺服器。為避免此問題，在順時針遍歷時只選取唯一的實體伺服器。

同一資料中心的節點常因電源中斷、網路問題、自然災害等原因同時故障。為提高可靠性，副本應放置於不同的資料中心，各資料中心之間透過高速網路連接。

## 一致性

由於資料被複製至多個節點，必須在各副本之間進行同步。**仲裁共識（Quorum Consensus）** 能保證讀寫操作的一致性。先定義幾個符號：

- **N** = 副本數量
- **W** = 寫入仲裁數。寫入操作須得到 W 個副本的確認才算成功。
- **R** = 讀取仲裁數。讀取操作須等待至少 R 個副本的回應才算成功。

以圖 6-6 的 N = 3 為例：

**W = 1** 並不代表資料只寫入一台伺服器。如圖 6-6 所示，資料複製於 s0、s1、s2 三台伺服器。W = 1 代表協調者（Coordinator）至少收到一個確認後，寫入操作即算成功。例如，若收到 s1 的確認，就不需要再等待 s0 和 s2。**協調者（Coordinator）** 作為客戶端與節點之間的代理（Proxy）。

W、R、N 的配置是延遲與一致性之間典型的取捨：

- 若 W = 1 或 R = 1，操作可快速回傳，因為協調者只需等待任一副本的回應。
- 若 W 或 R > 1，系統提供更好的一致性，但查詢會較慢，因為協調者必須等待最慢副本的回應。
- 若 **W + R > N**，強一致性得到保證，因為至少有一個重疊節點持有最新資料。

### 常見配置

| 配置                         | 說明             |
| ---------------------------- | ---------------- |
| R = 1, W = N                 | 針對快速讀取優化 |
| W = 1, R = N                 | 針對快速寫入優化 |
| W + R > N（通常 N=3, W=R=2） | 保證強一致性     |
| W + R ≤ N                    | 不保證強一致性   |

### 一致性模型

設計鍵值儲存系統時，一致性模型（Consistency Model）是另一個重要考量，它定義了資料一致性的程度：

- **強一致性（Strong Consistency）**：任何讀取操作都能回傳最新寫入的值，客戶端永遠不會看到過期資料。
- **弱一致性（Weak Consistency）**：後續讀取操作不一定能看到最新值。
- **最終一致性（Eventual Consistency）**：弱一致性的一種。給予足夠時間，所有更新都會傳播至所有副本並保持一致。

強一致性通常透過強制副本在接受新讀寫之前，等待所有副本同意當前寫入來實現。這種方式對高可用系統並不理想，因為可能阻塞新操作。Dynamo 和 Cassandra 採用最終一致性模型，這也是本章推薦的模型。

## 不一致性解決方案：版本化（Versioning）

複製能提高可用性，但會導致副本之間的不一致。**版本化（Versioning）** 與**向量鎖（Vector Locks）** 用於解決不一致問題。版本化代表將每次資料修改視為資料的一個新的不可變版本。

**範例說明**

如圖 6-7 所示，副本節點 n1 和 n2 持有相同的原始值。server 1 將名稱改為「johnSanFrancisco」，server 2 將名稱改為「johnNewYork」（圖 6-8），產生了版本 v1 和 v2 的衝突，無法直接解決。

**向量時鐘（Vector Clock）**

向量時鐘是與資料項目關聯的 `[伺服器, 版本]` 對，可用來檢查一個版本是先於、後於或與另一個版本衝突。

假設向量時鐘表示為 `D([S1, v1], [S2, v2], ..., [Sn, vn])`，若資料項目 D 被寫入伺服器 Si，系統必須執行以下操作之一：

- 若 `[Si, vi]` 已存在，則將 vi 遞增
- 否則，建立新條目 `[Si, 1]`

**具體範例（圖 6-9）**

1. 客戶端寫入 D1，由伺服器 Sx 處理 → 向量時鐘 `D1[(Sx, 1)]`
2. 另一個客戶端讀取 D1，更新為 D2 並寫回，仍由 Sx 處理 → `D2([Sx, 2])`
3. 另一個客戶端讀取 D2，更新為 D3，由伺服器 Sy 處理 → `D3([Sx, 2], [Sy, 1])`
4. 另一個客戶端讀取 D2，更新為 D4，由伺服器 Sz 處理 → `D4([Sx, 2], [Sz, 1])`
5. 另一個客戶端讀取 D3 和 D4，發現衝突（D2 被 Sy 和 Sz 同時修改），解決後由 Sx 寫回 → `D5([Sx, 3], [Sy, 1], [Sz, 1])`

**判斷規則**：

- 若版本 Y 中每個參與者的版本計數都大於或等於版本 X 中對應的計數，則 X 是 Y 的祖先（無衝突）。
- 若 Y 的向量時鐘中，有任何參與者的計數小於 X 中對應的計數，則兩者存在衝突（兄弟關係）。

**向量時鐘的缺點**：

1. 客戶端需要實作衝突解決邏輯，增加複雜度。
2. `[伺服器: 版本]` 對可能快速增長。解決方式是設定長度閾值，超過時移除最舊的對。這可能導致後代關係無法精確判斷，但根據 Dynamo 論文 [4]，Amazon 在生產環境中尚未遇到此問題。

## 故障處理

在大規模系統中，故障不僅不可避免，而且很常見。本節首先介紹故障偵測技術，然後討論常見的故障解決策略。

### 故障偵測

在分散式系統中，僅憑一台伺服器的說法認定另一台伺服器故障是不夠的。通常需要至少兩個獨立的資訊來源才能標記一台伺服器故障。

**全對全廣播（All-to-All Multicasting）** 是一種直接的解決方案，但當系統中有許多伺服器時效率較低（圖 6-10）。

更好的解決方案是使用去中心化故障偵測方法，如**八卦協議（Gossip Protocol）**：

- 每個節點維護一個節點成員清單，包含成員 ID 和心跳計數器。
- 每個節點定期遞增自己的心跳計數器。
- 每個節點定期向一組隨機節點發送心跳，這些節點再將心跳傳播至另一組節點。
- 節點收到心跳後，更新成員清單至最新資訊。
- 若心跳在超過預定期間後未增加，則該成員被視為離線。

**圖 6-11 說明（以 s0 為例）**：

- s0 維護左側顯示的節點成員清單
- s0 注意到節點 s2（成員 ID = 2）的心跳計數器長時間未增加
- s0 向一組隨機節點發送包含 s2 資訊的心跳；一旦其他節點確認 s2 的心跳計數器長時間未更新，s2 被標記為故障，並將此資訊傳播至其他節點

### 暫時性故障處理

透過八卦協議偵測到故障後，系統需要部署特定機制來確保可用性。在嚴格仲裁方式中，讀寫操作可能被封鎖。

**寬鬆仲裁（Sloppy Quorum）** [4] 用於提高可用性：系統為寫入選擇雜湊環上前 W 台健康的伺服器，為讀取選擇前 R 台健康的伺服器，忽略離線伺服器。

若某伺服器因網路或伺服器故障而無法使用，另一台伺服器將暫時處理請求。當故障伺服器恢復後，變更會被推回以實現資料一致性，此過程稱為**提示遞交（Hinted Handoff）**。在圖 6-12 中，s2 無法使用，s3 暫時處理讀寫請求；s2 恢復後，s3 將資料還給 s2。

### 永久性故障處理

提示遞交用於處理暫時性故障。若某副本永久無法使用，則需要實作**反熵協議（Anti-Entropy Protocol）** 來同步副本。反熵涉及比較副本間的每筆資料，並將每個副本更新至最新版本。

**Merkle 樹（Merkle Tree）** 用於不一致偵測，並將資料傳輸量降至最低。

> 引自 Wikipedia [7]：「雜湊樹（Hash Tree）或 Merkle 樹是一種樹狀結構，每個非葉節點以其子節點的標籤或值的雜湊值為標籤。雜湊樹允許對大型資料結構的內容進行高效且安全的驗證。」

**建構 Merkle 樹的步驟**（假設鍵空間從 1 到 12）：

- **步驟 1**：將鍵空間分成若干桶（Bucket）（圖 6-13 為 4 個桶），桶作為樹的根層節點以限制樹的深度。
- **步驟 2**：使用統一雜湊方法對每個桶中的鍵進行雜湊（圖 6-14）。
- **步驟 3**：每個桶建立一個哈希節點（圖 6-15）。
- **步驟 4**：透過計算子節點的雜湊值向上建構樹，直到根節點（圖 6-16）。

**比較兩個 Merkle 樹**：從比較根雜湊值開始，若根雜湊值相同，兩台伺服器資料相同；若不同，則依次比較左子節點和右子節點的雜湊值，遍歷樹找出未同步的桶並進行同步。

使用 Merkle 樹時，需要同步的資料量與兩個副本之間的差異成正比，而非與它們包含的資料總量成正比。在實際系統中，桶的大小相當大，例如每 10 億個鍵配置 100 萬個桶，每個桶只包含 1000 個鍵。

### 資料中心故障處理

資料中心故障可能因電源中斷、網路中斷或自然災害引起。為建立能夠處理資料中心故障的系統，重要的是將資料複製到多個資料中心。即使某個資料中心完全離線，用戶仍可透過其他資料中心存取資料。

## 寫入路徑（Write Path）

圖 6-19 說明寫入請求被導向特定節點後發生的事情（以 Cassandra 架構為主要參考 [8]）：

## 讀取路徑（Read Path）

讀取請求被導向特定節點後，系統首先檢查記憶體快取中是否有資料。若有，直接回傳給客戶端（圖 6-20）。

若資料不在記憶體中，則需從磁碟取得。系統需要一種有效率的方式找出哪個 SSTable 包含目標鍵，**布隆過濾器（Bloom Filter）** [10] 是解決此問題的常用方案。

**資料不在記憶體時的讀取路徑（圖 6-21）**：

1. 系統首先檢查記憶體中是否有資料，若無則進入步驟 2。
2. 若記憶體中無資料，系統檢查布隆過濾器。
3. 布隆過濾器用於判斷哪些 SSTable 可能包含該鍵。
4. SSTable 回傳資料集的結果。
5. 資料集結果回傳給客戶端。

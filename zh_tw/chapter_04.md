# 第 4 章：限流器設計（加強版）

## 1. 章節核心

限流器的目標是保護系統：避免流量突刺拖垮核心服務，並在攻擊或異常時維持可用性。

## 2. 限流維度

- 依使用者：防止單帳號濫用。
- 依 IP：防止來源攻擊。
- 依 API：保護高成本端點。
- 依租戶：多租戶公平性。
- 全域限流：保護整體基礎設施。

## 3. 常見演算法比較

### 固定視窗

- 優點：實作簡單。
- 缺點：視窗邊界可能被「雙倍突發」利用。

### 滑動日誌

- 優點：精準。
- 缺點：記憶體成本高。

### 滑動視窗計數

- 優點：精度與成本折衷。
- 缺點：實作略複雜。

### 令牌桶

- 優點：允許可控突發，工程上最常見。
- 缺點：需調整補充速率與桶容量。

### 漏桶

- 優點：輸出平滑、保護後端效果好。
- 缺點：對突發流量較不友善。

## 4. 落地架構建議

- 部署位置：API Gateway / Service Mesh / 應用層。
- 狀態儲存：Redis（原子計數 + Lua）。
- 回應策略：429 + Retry-After + 追蹤碼。
- 動態配置：熱更新、灰度發布、快速回滾。

## 5. 關鍵工程問題

- 分散式時鐘差異會影響視窗判定。
- 多節點一致性需透過共享儲存或分片規則。
- 要避免把限流器本身做成單點。
- 需監控誤殺率與漏放率，不只看命中率。

## 6. 故障與降級策略

- Redis 不可用：切本地保守限流模式。
- 規則服務故障：保留最近一次有效配置。
- 極端流量：啟用全域硬閘門，保護核心交易路徑。

## 7. 面試可直接總結

「我會用令牌桶作為主策略，API Gateway 統一執行；計數狀態放 Redis 並用 Lua 保證原子性；同時保留本地降級模式，避免 Redis 故障導致全面失控。最後用監控閉環調參，平衡誤殺與保護效果。」
